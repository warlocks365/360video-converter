# 360 Video Converter v3.14.8

修复版本：合并/超长视频转换后，全景元数据"看似没打上标签"的误报问题。

## 问题现象

合并转换中已勾选「注入 GSpherical 全景元数据」，但转换完成后，元数据报告或元数据工具里该文件显示"无全景元数据"，看起来标签没有打上。

## 实际根因（重要澄清）

**编码注入本身是成功的**——用 ffprobe 直接检查合并产物，可以确认 Spherical Mapping（equirectangular）标签确实已写入，YouTube / 群晖 Photos 等平台能够正常识别为 360° 全景。

误报来自应用**自己的检测逻辑缺陷**：读取 GSpherical 标签的函数只扫描文件开头和结尾各 4MB 的范围。合并后的视频索引表（moov）非常大（实测 87GB 合并产物的 moov 达 13MB），GSpherical 标签位于索引表深处（距文件头约 8MB），超出了扫描窗口，于是被漏检——报告就把它错误地标成"无全景元数据"。

## 修复内容

全景元数据检测重写为：先精确定位 MP4 索引表（moov）盒的位置，再在索引表范围内完整搜索 GSpherical 标签——不再受固定 4MB 窗口限制，任意大小的合并产物都能正确识别。

同时受益的场景：
- 元数据报告的全景标签列不再误报"无"；
- 元数据工具批量列队的"全景元数据"筛选与自动开关正确；
- 全景视频防抖的类型判定（依赖同一检测）不再误选标准防抖算法。

## 验证

| 项 | 结果 |
|---|---|
| 合成回归：大索引表文件（旧法必漏/新法必中对照、跨块边界、防假阳性、注入三路径往返） | 13/13 |
| 87GB 真实合并产物经打包版接口检测 | has_spherical=True（360°/mono），与 ffprobe 一致 |
| 门禁 01–11（含打包 e2e 20/20） | 全绿 |
| 既有回归：三功能 19/19、queue 185/185、report 29/29 | 零劣化 |

## 升级建议

此前合并转换的产物若被报告标记为"无全景元数据"，升级 v3.14.8 后重新探测即可看到真实标签（文件本身无需重转）。
