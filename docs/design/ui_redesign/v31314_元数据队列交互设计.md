# 360° Video Converter — 元数据队列交互设计规格

> 版本：v3.13.14 设计增量 | 日期：2026-02-14 | 设计：颜好看
> 基准：`static/css/theme-cobalt.css`（方案 D 深海钴蓝，v3.13.12 锁定）+ `static/css/app.css`（基础层）

### 0.2 本次设计必须解决的 5 个真实风险

| 风险 | 后果 | 本规格的处置 |
|------|------|-------------|
| 同一个「应用元数据」按钮，有时跑队列、有时跑界面 | 用户无法预判，误以为改了界面设置生效 | 按钮文案随状态切换 + 惰性化界面设置 + 执行时写入日志（0.3） |
| 「已完成」项留在队列里，用户想让它重跑 | 静默无操作（已完成项不重跑），用户以为改了生效 | **操作列「重排队」按钮显式改回「待转换」**（6.4，`reset-meta-item` 零副作用） |
| 「读创建时间」被误解为「视频拍摄时间」 | 写入错误的拍摄日期，且难以察觉 | 字段级 tip + 常驻说明块 + 溯源条三处措辞统一（4.1） |
| 输出目录来源不透明 | 同一批文件被写到不同目录且无从追溯 | 每一行任务栏常驻输出归属芯片，三态可见（2.4） |
| 存量队列徽标用了 emoji（`&#127760;` `&#128197;` `&#128205;`） | 违反 P0，且与新增 SVG 图标形成双图标体系 | 同批替换为描边 SVG（7.4），不跨版本遗留 |

### 0.3 需要纠正的一处输入前提

需求 8 把「1024x640 最小窗口」与「1180px 单列回落断点」并列为两种情况。**实际上 `min_size` 1024px < 单列断点 1180px，二者属于同一套布局 regime**：`app.css:91` 的 `@media (max-width:1180px)` 已经覆盖了从 1024 到 1180 的全部宽度。真正的第二种情况是 **1181-1279px**（三栏仍在，但中栏被压窄）。本规格按「单列 regime（<=1180px）」与「窄三栏 regime（1181-1279px）」两段分别校验（12 节）。

## 2. 新增 Design Token（C-extension 层）

### 2.1 为什么必须新增令牌

浅色主题实测（见 11 节）：`--success` `#149a6e` 在白底上对比度 **3.57:1**、`--warning` `#b47b1b` **3.63:1**、`--error` `#d9534f` **3.96:1**、`--accent` `#14907f` **3.94:1**，四者**全部低于 WCAG AA 正文 4.5:1**。若状态文案直接使用这四个令牌，浅色主题下的队列状态列不可读。

因此新增 5 枚「状态前景色」令牌：暗色下直接别名既有令牌（零视觉变化），浅色下用 `color-mix()` 向 `--text` 收拢至 AA 以上。**不硬编码任何色值**（P0）。

### 2.2 追加到 `static/css/theme-cobalt.css`（可直接粘贴）

```css
/* ══ v3.13.14 元数据队列：状态前景令牌 ══════════════════════════
   暗色下直接别名既有令牌（实测 5.16:1 ~ 9.55:1，全部 AA 通过）；
   浅色下把语义色向 --text 收拢。

   混色比例的取值依据（WCAG 2.1 实测，非目测）：
   浅色主题下这些令牌有「两种承载体」——表格的 --surface（白）与
   各类 *-light 浅色底（如 .scope-notice 的 --warning-light 复合底）。
   实测在 80-84% 区间时，白底达标（4.9-5.1:1）但**浅色底不达标
   （4.18-4.45:1）**。故统一收拢至 72%，使两种载体同时通过：
     running  72% -> 白底 5.99 / 浅底 5.20
     done     72% -> 白底 5.56 / 浅底 4.85
```

### 2.4 两条令牌层决策说明

| 决策 | 理由 |
|------|------|
| 状态芯片**用透明底 + 1px 描边**，不用 `--success-light` 等半透明填充 | 填充底会把 `--state-done-fg` 从白底 5.56:1 拉低到 4.85:1、把 `--primary` 从 4.70 拉低到 4.52:1（余量归零，已按 alpha 复合复算）。透明底 + 描边既保住对比度，视觉重量也低于填充，与既有 `.meta-badge`（`app.css:564-581`，同为描边 + 半透明底）的观感一致 |
| 「读创建时间」「跟随全局」两枚芯片文字用 `--text-secondary`，**不用 `--text-muted`** | `--text-muted` 在暗色 `--surface` 上仅 **2.88:1**、浅色白底上 **2.84:1**，两个主题都不合格。现有 `renderMetaBatchTable` 用它画「等待中」（`50-meta.js:347`）是一处既存缺陷，本次随状态列一并修正 |

## 3. 改动一：「加入批量列队」按钮

### 3.1 位置（精确到相邻关系）

`#mainActionBar` 内的按钮序列调整为：

```
#startBtn  →  #metaApplyBtn  →  #metaAddQueueBtn（新）  →  #pauseBtn  →  #cancelBtn  →  #testEncodeLabel  →  .progress-section
```

即：**紧贴「应用元数据」右侧**，`#pauseBtn` 之前。视觉上与主 CTA 同属一组（gap 12px，`app.css:458`），中间不插入分隔线。

`#metaAddQueueBtn` 的显隐跟随既有 `switchMode` 模式（`10-ui.js:52-55`）：

```js
// switchMode() 内，紧随 setDisplay('metaApplyBtn', ...) 之后
setDisplay('metaAddQueueBtn', isMetaMode ? '' : 'none');
```

- 元数据模式：显示
- 单文件 / 合并 / 批量 / 报告 / VR3D：隐藏（转换族已有自己的 `#addToBatchBtn`，两者不同时出现，避免同名不同义）

### 3.2 控件规格

| 项 | 值 |
|----|-----|
| id | `metaAddQueueBtn` |
| class | `btn btn-lg`（**不加 `btn-primary`**） |
| 标签 | `加入批量列队` |
| 图标 | `inbox` 描边 SVG，**20px**（`btn-lg` 字号 1rem，14px 会显得 undersized） |
| 高度 | 与 `#metaApplyBtn` 完全一致（同为 `btn-lg`，由 class 保证，差值 0px） |

**为什么不给主按钮样式**：动作栏内已有唯一主 CTA「应用元数据」（`btn-primary btn-lg` + 品牌渐变）。若新增第二个 `btn-primary`，同一屏出现两个渐变实心块，违反「每屏强调色 <= 2 处」并制造决策竞争。加入队列是「准备」动作，执行才是「提交」动作。

### 3.4 状态矩阵（5 态）

| 状态 | 触发条件 | 按钮表现 | 文案 / 反馈 |
|------|---------|---------|-----------|
| Default | `#metaInput` 有值 | 常态可点 | — |
| Hover | 指针悬停 | 背景 `var(--surface-hover)`，边框 `var(--text-muted)`（沿用 `app.css:206`） | 150ms |
| Focus | 键盘 Tab | `box-shadow: var(--focus-ring)`，**不移除 outline 之外任何可见指示** | 150ms |
| Active | 按下 | `transform: translateY(0.5px)` 不采用（会让 76px 吸底栏抖动）；仅背景加深一档 | 100ms |
| Disabled | `#metaInput` 为空 | `disabled` + `opacity: 0.5`（`app.css:217`）+ `cursor: not-allowed` + `title="先在上方「视频文件」选择一个文件"` | 鼠标无需点击即可获知原因 |
| Busy | 快照写入中（同步，通常 < 16ms） | `data-busy="1"` 禁用重复点击；**不引入 spinner**（操作是同步的，闪一下反而是噪音） | — |

## 4. 改动二：编辑弹窗补齐「输出目录」+ 输出归属三级表达

### 4.1 数据契约（前端与后端共用，务必先对齐）

每个队列项 `metaBatchItems[i]` 新增一个字段，**不并入 `collectMetaSettings()`**：

```js
// f.outDir = {
//   mode:  'global'   | 'snapshot' | 'inplace',
//   value: string     // 仅 mode==='snapshot' 时有效，为加入时快照的目录绝对路径
// }
```

**为什么不放进 `collectMetaSettings(prefix)`**：该函数被 `p_` / `m_` / `me_` 三套前缀共用，字段由 `META_FIELD_IDS` 表驱动。`p_` 与 `m_` 侧没有「输出位置」控件，若把 `out_mode` 塞进归一化对象，`checked('outMode')` 对缺失元素恒返回 `false`，两个前缀会静默拿到 `mode: 'inplace'`，污染 `/api/apply_metadata` 的下发参数。**输出位置是队列项属性，不是元数据设置项**，必须在 `saveMetaFileSettings()` 里独立读写。

**文案变更说明**：
- `等待中` -> `待转换`。前者描述时间，后者描述状态，与「加入批量列队 / 应用元数据」的动词体系一致。

- `&#10003; 完成 (1.2s)` -> `完成 1.2s`。勾号改为 SVG `check`（P0），括号改为空格以省 4px 给 100px 列宽。

宽度复算（100px 列，`td` 左右 padding 各 12px → 内容区 76px）：
- `待转换` 3 字 x 12px = 36px OK
- 12px spinner + 4px gap + `处理中` 36px = 52px OK
- 14px check + 4px gap + `完成` 24px + 4px + `1.4s` 24px = 70px OK
- failed 两行：14+4+24 = 42px（第一行）/ 11px x 1.4 = 15px（第二行），行高 8+42+15+8 = **73px**

> 唯一允许的行高变化就是 failed 的两行。它不改列宽、不改表格结构，属可接受代价；换来的是失败原因不用去悬停才能看到。

**三条刻意的克制**：

1. **不用整行 `opacity`**。`opacity: 0.55` 会让已完成行的文字落到 2.6:1（暗色）/ 2.1:1（浅色），远低于 AA。改为只把「已无信息增量」的两列（序号、文件名）降到 `--text-secondary`（6.10:1 / 6.73:1），其余保持原色。

3. **不新增行级背景色区分**（除 running）。已完成的语义已经由「完成 + check 图标 + 文件名降一档」三重冗余编码表达，再加底色会让 500px 高的表格变成色块噪声。

### 6.4 规则 R7：已完成项的「重排队」出口

用户确认的决策是「执行后标记完成并保留在列队，再次点击只跑未完成项」。该决策本身正确，但副作用是：用户改了设置、点了执行、什么都没发生，且**没有任何提示**——这是静默的数据信任损伤，必须在 UI 上闭环。

v3.13.14 裁决：本条**以显式按钮实现**（`reset-meta-item`），不再依赖「编辑后自动回落」的隐式行为。

#### 6.4.1 按钮规格

| 项 | 值 |
|----|-----|
| 位置 | 操作列，**位于「编辑」与「移除」之间** |
| `data-action` | `reset-meta-item` |
| 图标 | `ico-reset`（`rotate-ccw` 类，14px，见 7.3） |
| 文案 | 纯图标（无文字），`title` / `aria-label`：`重排队：改回待转换，下次点应用时重跑该项` |
| 变体 | `class="btn btn-sm"`（**不加 `btn-danger`**，它不是破坏性操作） |
| 显隐 | **仅 `f.status === 'done'` 时渲染**；其余状态不生成该按钮 |
| disabled | `running` 行不渲染该按钮（该行本就是 pending 语义，无重排需求） |

渲染逻辑（`renderMetaBatchTable` 的操作列）：

```js
const isDone = f.status === 'done';
const resetBtn = isDone
  ? `<button class="btn btn-sm" data-action="reset-meta-item" data-idx="${i}"
       title="重排队：改回待转换，下次点应用时重跑该项"
       aria-label="重排队：改回待转换，下次点应用时重跑该项">${ICO.reset(14)}</button>`
  : '';
```

#### 6.4.2 行为（零副作用）

| 触发 | 行为 |
|------|------|
| 点击 `reset-meta-item` | 仅改状态：`f.status='pending'`、`f.statusMsg=''`、`f.duration=''`；`f.settings` **保持不变**；不调用任何执行函数 |
| 反馈 | Toast：`第 5 项已改回待转换，下次点「应用元数据」时会重跑`（type=info，2500ms） |
| 徽标 | 立即重算：待转换 +1、已完成 -1（走 8.3 的统一 sync） |
| 勾选框 | 不改变勾选状态 |

> **为什么 reset 不触发任何执行**：若按钮直接跑 ffmpeg，用户点一下就意外启动批量处理——在 500 项的队列上这是灾难性误操作。reset 只改状态，执行必须由用户显式点「应用元数据」，保持「准备」与「提交」分离（与 D1 中加入队列不自动执行的同理）。

#### 6.4.3 操作列宽度预算（**90px 内放不下三个默认按钮**）

现状实测：`.btn-sm` = `padding 6px 10px`（`app.css:218`）+ 图标 14px + border 1px x 2 = **36px/个**。操作列声明 `width:90px`（`index.html:833`），扣除 `td` 左右 padding 各 12px（`app.css:327`）后可用 **66px**。

| 方案 | 占用 | 结论 |
|------|------|------|
| 现状 2 个按钮（36 x 2 + gap 4） | 76px | **已溢出 10px**（既有缺陷，`.table-wrap` 有 `overflow-x:auto` 兜底，未暴露） |
| 3 个默认按钮（36 x 3 + gap 4 x 2） | 116px | 需列宽 **140px**，超出 50px，不可接受 |
| 3 个紧凑按钮（`padding 6px 4px` = 24px，gap 3px） | 24 x 3 + 3 x 2 = **78px** | 仍超 66px |
| **3 个紧凑按钮 + 操作列 90 -> 104px** | 78px vs 可用 80px | **采用** |

采用的 CSS（追加到 `theme-cobalt.css`，只影响元数据队列操作列）：

```css
/* 元数据队列操作列：三按钮紧凑排布
   预算：列宽 104px - td padding 24px = 80px 可用；实际占用 78px。
   按钮 24px = padding 6px 4px + icon 14px + border 2px。 */
#metaBatchTableBody td.col-actions { white-space: nowrap; }
#metaBatchTableBody td.col-actions .btn-sm { padding: 6px 4px; }
#metaBatchTableBody td.col-actions .btn-sm + .btn-sm { margin-left: 3px; }
```

表头同步改宽（`index.html:833`）：`<th style="width:104px;">操作</th>`。

> **代价与取舍**：操作列 90 -> 104px，中栏表格的「任务内容」列被压缩 14px。因任务内容芯片容器已设 `max-height:44px`（2.2 节），压缩后芯片换行增多但**不会撑高行高**，可控。若 frontend 反馈中栏过窄，可改为 96px + 按钮 `padding 6px 3px`（每按钮 22px，合计 72px，可用 72px）——恰好卡满，不推荐，余量为 0。

#### 6.4.4 键盘与无障碍

| 项 | 规格 |
|----|------|
| 可达性 | 原生 `<button>`，Tab 可达；`aria-label` 与 `title` 同文案，避免图标按钮无障碍名称为空 |
| 焦点顺序 | 编辑 -> 重排队 -> 移除（DOM 顺序即视觉顺序） |
| 触达尺寸 | 24 x 26px（宽 x 高）。**低于 WCAG 2.5.5 建议的 44px**，但符合 2.5.5 目标尺寸的「spacing」例外（相邻目标中心间距 >= 24px，见下方计算） |
| 中心间距 | 三按钮中心间距 = 12（半按钮）+ 3（margin）+ 12 = **27px >= 24px**，满足 2.5.5 spacing 例外 |
| 减性 | 无动效需求（纯状态切换，200ms 内完成） |

> 桌面 WebView 场景（非触摸优先），且 2.5.5 的 spacing 例外成立，故不为此把列宽进一步放大。

## 7. SVG 图标规格

### 7.1 统一规格（全表适用）

```
viewBox="0 0 24 24"  fill="none"  stroke="currentColor"
stroke-width="2"    stroke-linecap="round"  stroke-linejoin="round"
aria-hidden="true"  focusable="false"
```

- 与 `index.html:22-40` 现有 5 枚图标（theme / single / merge / batch / metadata / vr3d）**逐属性一致**，零视觉断层
- 尺寸档：**14px**（`.btn-sm` 内、表格内联、芯片内）/ **20px**（`btn-lg` 内）。**不提供 16px 档**，避免第三档尺寸造成基线漂移
- `currentColor` 继承文字色，因此换肤/换色自动跟随，不需要 `fill` 覆盖
- **全部为单色描边路径，无填充块**。这是 14px 下唯一能保证可辨识的画法

### 7.2 复合图标的禁用说明

需求提出「加入队列（layer/plus 类）」。**本规格采用单枚 `inbox` 而非 `inbox + plus` 合成**，理由是算术而非偏好：14px 下 24 网格的 1 单位 = 0.58px，一个 5 单位的 plus 臂实际只有 2.9px，渲染后是一团糊。合成图标只在 20px 以上才成立（5 单位 = 4.2px，仍偏弱）。「加入」的语义由按钮文案「加入批量列队」承担，图标只负责「队列/托盘」这一物。

同时**不复用现有 `layers` 图标**（`index.html:37` 批量转换页签）：动作栏已有「加入批量队列」（转换族，`index.html:1091`），若元数据侧也用 `layers`，两个不同队列的按钮会长得一模一样。

## 8. `#metaQueueCount` 徽标计数规则

### 8.1 单一格式规则（覆盖需求列出的四种情形）

```
[状态点] {总数} 项  ·  X 待转换  ·  Y 已完成  ·  Z 失败  ·  勾选 S
```

每个片段**仅在计数 > 0 时出现**。`总数 = X + Y + Z`。

| 需求情形 | 渲染结果 | 状态点颜色 |
|---------|---------|-----------|
| 空（总数 0） | **整个徽标隐藏**（`classList.add('hidden')`） | — |
| 有待转换（X>0，Y=0，Z=0） | `4 项 · 4 待转换` | `--primary` |
| 全部完成（Y=总数，X=0，Z=0） | `4 项 · 4 已完成` | `--success` |
| 混合（X>0 且 Y>0） | `4 项 · 2 待转换 · 2 已完成` | `--primary` |
| 混合含失败 | `4 项 · 2 待转换 · 1 已完成 · 1 失败` | `--error` |
| 部分勾选（0 < S < 总数） | 上述 + ` · 勾选 2` | 同上 |
| 全选 | **不显示** `勾选` 片段（S == 总数时无信息量） | 同上 |

## 10. 「读创建时间」失败态设计

### 10.1 铁律

> **失败绝不覆盖已有值。** 任何失败路径都不得清空或修改 `#*_manual_date` 中用户已输入的内容。用户的时间可能是手打了一小时的成果，一次误点不能毁掉它。

### 10.2 四种失败情形

| 情形 | 检测来源 | Toast 文案（type / 时长） | 溯源条 | 恢复路径 |
|------|---------|------------------------|--------|---------|
| 用户取消文件对话框 | `/api/browse` 无 `path` 返回 | **不弹**（取消不是错误） | 保持原状 | 用户自行继续 |
| 文件已被删除 / 移动 | `FileNotFoundError`（HTTP 404） | `读不到创建日期：文件已不在 {目录}`（error / 6000ms） | `未能读取创建日期 · 手动输入` | 「手动输入」按钮：焦点移入输入框 + 全选 |
| 无访问权限 | `PermissionError`（HTTP 403） | `读不到创建日期：没有读取 {文件名} 的权限`（error / 6000ms） | 同上 | 同上；`title` 追加 `请确认该文件未被其他程序独占，或把文件复制到可读位置后重试` |
| 其他 IO 异常 | 其他 `OSError` | `读取创建日期失败：{归一化后的中文短句}`（error / 6000ms） | 同上 | 同上 |

### 10.3 错误信息的两段式原则

**Toast 只给人话，系统细节进 `title` 与日志**：

| 层 | 内容 | 理由 |
|----|------|------|
| Toast 主体 | 「读不到创建日期：没有读取 X.mp4 的权限」 | 用户要的是「发生了什么 + 怎么办」 |
| Toast / 溯源条 `title` | `系统返回：PermissionError [WinError 5] 拒绝访问` | 研发与进阶用户的排障入口，不占据首屏 |
| `#logBox` | `[日期] 读取创建时间失败 {path}：{完整异常}` | 事后可追溯，与既有 `00-core.js:16` 的全局错误日志同一约定 |

**禁止**把 `e.message` / 异常栈直接拼进 Toast。`50-meta.js:323` 现有的 `alert('打开文件对话框失败: ' + e.message)` 是反面样本，本次新增路径不复制该做法。

### 10.4 「手动输入」恢复按钮的准确定位

它**不是**一个提交按钮，是「放弃自动读取、改为自己敲」的跳转。行为三连：

1. `#*_manual_date` 聚焦
2. 全选现有内容（`input.select()`），可直接覆盖
3. 溯源条从 `error` 切到 `manual`，文案改为 `手动输入，未从文件读取`

不做的事：不弹窗、不清空、不自动切换到别的日期来源（用户可能确实想用文件日期，只是这次没读到）。

## 11. 浅色主题适配检查点

### 11.1 对比度实测（WCAG 2.1）

测量基准：暗色取 `--surface` `#131a2c`；`.card` 实际有 `linear-gradient(180deg,#151d31,#131a2c)` 覆盖层（`theme-cobalt.css:113-115`），故另列「浅底」一档按较亮端 `#151d31` 复算。浅色取 `#ffffff`，并对 `*-light` 类浅色底按 alpha 复合后另算一档（见 11.2 陷阱 3）。

| 用途 | 令牌 | 暗色/白底 | 暗色/浅底 | 浅色/白底 | 浅色/浅底 | 判定 |
|------|------|-----------|-----------|-----------|-----------|------|
| 正文 / 文件名 | `--text` | 14.61 | 13.9 | 17.33 | - | AA 通过 |
| 状态 pending / 芯片次要文字 | `--state-pending-fg` | 6.10 | 5.90 | 6.74 | - | AA 通过 |
| 状态 running | `--state-running-fg` | 9.55 | 8.9 | 5.99 | 5.20 | AA 通过 |
| 状态 done | `--state-done-fg` | 9.01 | 8.4 | 5.56 | 4.85 | AA 通过 |
| 状态 failed | `--state-failed-fg` | 6.26 | 5.9 | 6.13 | 5.26 | AA 通过 |
| 原地芯片 / 说明条 | `--state-caution-fg` | 9.19 | 8.7 | 5.64 | 4.94 | AA 通过 |
| 快照芯片文字 | `--primary` | 5.42 | 5.2 | 4.70 | 4.52 | AA 通过（浅色/浅底余量仅 0.02，**必须用透明底芯片**） |
| 输入框内文字（底色 `--bg`） | `--text` | 14.61 | - | 17.33 | - | 通过 |
| `.meta-form-inert` 内文字 | `--text-secondary` @ opacity .55 | 约 2.6 | - | 约 2.5 | - | WCAG 禁用控件豁免（见 11.2 陷阱 5） |

> 全部数值由 WCAG 2.1 相对亮度公式复算得出，非目测。「浅底」一栏指文字落在 `*-light` 浅色底上的情形（如 `.scope-notice`、`.info-box`）。

### 11.2 五个必须处理的浅色陷阱

| # | 陷阱 | 处置 |
|---|------|------|
| 1 | 语义色在浅色下全部低于 4.5:1（`--success` 3.57 / `--warning` 3.63 / `--error` 3.96 / `--accent` 3.94） | 引入 `--state-*-fg` 五枚令牌（2.2）。**本设计的核心浅色改动** |
| 2 | `--text-muted` 双主题均不合格（2.88:1 / 2.84:1），但现有代码在「等待中」用它（`50-meta.js:347`） | 状态列 pending 改用 `--state-pending-fg`（= `--text-secondary`）。顺手修掉既存缺陷 |
| 3 | **令牌必须同时在「白底」与「浅色底」两种载体上达标**——本次最隐蔽的坑。初版把混色比例取在 80-84%，实测白底 4.90-5.13:1 达标，但落到 `--warning-light` 底上只剩 4.18-4.45:1，**不达标** | 全部收拢到 **72%**（2.2 附实测表），两种载体同时通过，最低 4.85:1。代码注释已标注「勿为更鲜艳调回 80%+」 |
| 4 | 芯片若用 `--success-light` 等半透明填充底，复合后 `--state-done-fg` 从 5.56 掉到 4.85；`--primary` 从 4.70 掉到 4.52（余量归零） | 芯片一律**透明底 + 描边**（2.4）。既保住对比度，视觉重量也低于填充 |
| 5 | `.meta-form-inert` 的 `opacity: 0.55` 使惰性区文字落到约 2.6:1 | 属 WCAG 对「禁用控件」的明确豁免，可接受。**但说明条必须在惰性子树之外**（5.2），保证「为什么不生效」这句关键信息始终满对比度 |

### 11.3 浅色下的额外检查项

| 检查项 | 结论 |
|--------|------|
| 芯片虚线描边（`--chip-border-neutral` = `text-secondary` @26%）在白底上是否可见 | 可见但偏弱。判定为可接受：它是**冗余编码**（配合「跟随全局」文字与 `link` 图标），不承载唯一信息 |
| 品牌渐变（`linear-gradient(135deg,#2f6fe0,#14907f)`）上的 20px `inbox` 图标 | `--on-primary` 深色前景压在渐变上，浅色主题下渐变两端亮度均低于暗色主题，对比度更高，无问题 |
| `.date-source.is-error` 文字 | 走 `--state-failed-fg`，白底 6.13 / 浅底 5.26，通过 |
| `--primary` 在浅色/浅底仅 4.52:1 | 余量极薄。**因此快照芯片必须用透明底**（陷阱 4）。若后续有人给芯片加填充底，该项立即跌破 AA |
| 已完成行降级为 `--text-secondary`（6.74:1） | 通过。**注意不可用整行 opacity**（会掉到约 2.9:1），这是 6.3 节刻意克制的原因之一 |

## 15. 风险与遗留
