## 三、维度详解

### ① 技术栈健康度 — 15/25

**做得好的：**

- **零依赖风险**：`static/` 目录顶层只有 `index.html`、`map-diagnostic.html`、`leaflet/` 三项。Leaflet 已完整本地化（含 marker 图标与 CSS 内引用的 layers 图标），彻底规避了 CDN 静默失败问题。这在桌面应用中是正确的工程决策。
- **无供应链攻击面**：没有 npm / node_modules / lock 文件，也就不存在幽灵依赖、依赖投毒、版本漂移问题。
- **无框架升级负担**：原生 JS 不会因为框架大版本变更而产生迁移成本。

**扣分项：**

| 问题 | 现状 | 影响 |
|------|------|------|
| 无 TypeScript | 4290 行纯 JS，仅靠 JSDoc 缺失 | 参数对象结构（`collectParams()` 返回约 60 个字段）无编译期校验，字段名拼写错误只能在运行时暴露 |
| 无 ESLint / Prettier | 无任何规范工具链 | 缩进、命名、分号风格全靠人工维持；`bare except` 类问题无法被静态发现 |
| 无单元测试 | 0 个测试文件 | 170 个函数中，纯函数（`esc`/`formatDuration`/`fmtTime`/`gcj02ToWgs84`/`min_level_for_pixels` 等）本可低成本覆盖 |
| 无构建流程 | 直接编辑源文件 | 无法做 tree-shaking、压缩、CSP 兼容处理 |

**改进方向**：不强求引入框架。**最低成本高收益的做法是引入 JSDoc 类型注解 + `tsc --checkJs` 做类型检查**（不产出构建物，纯校验），可将参数对象的字段错误从运行时提前到开发期。同时补 3 个纯函数测试文件（用 Node 内置 `node:test`，零依赖）。

### ② 架构设计模式 — 12/25

这是本次评审发现最集中问题的维度。三个结构性问题：

#### 问题 2.1：`pollStatus` 被「覆盖式补丁」重写，原实现沦为 79 行死代码 ⚠️ 严重

| 位置 | 内容 |
|------|------|
| 第 4077–4155 行 | `function pollStatus()` 原实现（79 行，处理编码任务状态） |
| 第 4888 行 | `const _origPollStatus = pollStatus;` — **保存了原函数，但全文件再无任何调用** |
| 第 4889–5120 行 | `pollStatus = async function() { ... }` — **直接重写函数引用** |

后果：
1. 第 4077–4155 行的原实现**永远不可能被执行**，成为 79 行死代码，误导后续维护者。
2. 第 4888 行的 `_origPollStatus` 是**死变量**，保存动作本身说明作者当时意图是「包装」，但最终选择了「替换」。
3. 重写版本（4898–4917 行）在**每一个轮询周期**（500ms）同时写入两套进度 DOM：`overallProgress`/`progressPercent`/`fileProgress` 与 `metaOverallProgress`/`metaProgressPercent`/`metaFileProgress`。而实际运行时**必定有一套处于隐藏状态**——即每 500ms 有 6 次无效 DOM 写入。

> **这是元数据功能「追加式开发」留下的结构痕迹**：为了不破坏已有代码，作者选择在文件末尾重新赋值函数，而非重构原有逻辑。

#### 问题 2.2：`jobId` / `pollTimer` 全局单例跨模式共用 ⚠️ 严重

```javascript
// 第 1826–1827 行
let jobId = null;        // 全模式共用
let pollTimer = null;    // 全模式共用
```

五个写入点全部指向同一变量：

| 行号 | 所属函数 | 模式 |
|------|---------|------|
| 3868 | `startVR3D()` | VR 3D 合成 |
| 3964 | `startConversion()` | 单文件 / 合并 / 批量 |
| 4854 | `startMetadataApply()` | 元数据工具 |

**风险场景（已通过代码路径确认）**：
1. 元数据任务运行中 → 用户切换到「单文件转换」模式 → `switchMode()`（1893–1923 行）**不停止任何轮询**，也不重置 `jobId`。
2. 用户点击「开始转换」→ `startPolling()`（4071–4075 行）执行 `clearInterval(pollTimer)` 后重新 `setInterval`，并用新任务的 id **覆盖 `jobId`**。
3. 此时元数据任务的轮询被夺走，其进度条**永久停留在最后一次状态**，取消/暂停按钮也会错误地作用于新任务。

`switchMode()` 只切换 CSS 可见性（`.hidden` / `display`），**不重置任何输入状态，也不停止任何轮询**——模式切换在语义上应该是「切换工作区」，但实现上是「切换显示」。

#### 问题 2.3：三个轮询器无仲裁并发

| 轮询器 | 位置 | 间隔 | 目标容器 |
|--------|------|------|---------|
| `pollStatus` | 4074 | 500ms | `#logBox` + 两套进度 DOM |
| `pollReportJob` | 5209 | 400ms（自递归 `setTimeout`） | `#reportLogBox` |
| `pollSysMon` | 4168 | 2000ms | `#sysmonCard` |

三者机制不统一（两个 `setInterval` + 一个自递归 `setTimeout`），且无统一生命周期管理。`reportJobId`（5131）与 `jobId` 完全隔离（经全文件检索确认），因此**报告任务本身不会串台**——但它引入了第三套并发的调度路径，且 `switchMode()` 同样不会停止它。

**附带发现的两个死变量：**
- 第 1828 行 `let currentParams = {}` — 声明后全文件从未使用
- 第 4888 行 `const _origPollStatus` — 同上

#### 问题 2.4：`build_cmd()` 的三分支 `elif` 串（设计亮点，值得保留）

相对而言，后端这一处设计是本项目的正面样本，前端改造时应借鉴同样的边界清晰化思路：

```
第一优先级：Okaa 接缝融合   (okaa_correction = true)
第二优先级：Insta360 处理   (is_insv_file() 且启用 stitch/denoise)
第三优先级：标准 vidstab+scale（默认路径）
```

三分支互斥、通过 `elif` 串联、避免滤镜冲突。**这正是前端「模式 → 处理路径」应该采用的写法**。

### 5.2 关键结论：项目存在**两套并行的 UI 架构**

```
「转换族」= 单文件 + 合并 + 批量 + VR3D
    └─ 共享 #encodePanel（716–1146）+ 共享 .action-bar（1530–1560）
    └─ 依赖全局 jobId + pollStatus

「元数据族」= 元数据工具 + 元数据报告
    └─ 自有设置区（m_ 前缀）+ 自有 .action-bar（1451–1472）
    └─ 元数据工具复用 jobId/pollStatus；元数据报告完全独立
```

**这是"整体统一性"缺失的根源**：不是风格细节不一致，而是**同一件事（配置参数、启动任务、观察进度、读取状态）在项目里有两套实现**。

「转换族」共享 `#encodePanel` 是一个**正确的 DRY 决策**，说明作者具备复用意识；但元数据族没有纳入同一套复用体系，而是平行复制了一份——第 4889 行的 `pollStatus` 覆盖式补丁正是这两套架构的**缝合痕迹**。

### 5.3 依赖耦合方向

```
DOM（id 选择器）  ←───  所有 JS 函数通过 document.getElementById 直接读写
       ↑
       └── 无中间状态层、无组件边界、无事件总线
```

- **169 个函数之间无显式依赖声明**，全部通过全局 DOM 与全局变量通信。
- 唯一存在的「模块化」痕迹是函数命名前缀（`collect*` / `render*` / `toggle*` / `poll*`），属于命名约定而非结构约束。
- **改造风险可控点**：正因为所有耦合都通过 DOM id 实现，只要**保持 id 不变**，重构 DOM 结构与 JS 组织方式都不会破坏功能——这是后续改造最重要的安全边界。

## 八、调度机制重构方案

### 8.1 目标架构

```javascript
// 1｜任务注册表取代全局单例
const JobRegistry = {
  jobs: new Map(),                    // jobId → { type, state, mountEl }
  register(id, type, mountEl) { this.jobs.set(id, { type, state: 'running', mountEl }); },
  get(id) { return this.jobs.get(id); },
  finish(id) { this.jobs.delete(id); },
};

// 2｜单一 Poller 取代三个并发定时器
const Poller = {
  timer: null,
  active: new Set(),                  // 活跃 jobId 集合
  tick() {
    for (const id of this.active) {
      const job = JobRegistry.get(id);
      if (!job) { this.active.delete(id); continue; }
      fetchJobStatus(id).then(data => Renderers[job.type](data, job));
    }
  },
  start() { if (!this.timer) this.timer = setInterval(() => this.tick(), 500); },
  stop()  { clearInterval(this.timer); this.timer = null; },
};

// 3｜按任务类型分派渲染，每套渲染只写自己的 DOM
const Renderers = {
  encode:   (data, job) => { /* 只写 #overallProgress 等 */ },
  metadata: (data, job) => { /* 只写 #metaOverallProgress 等；含 _metaProcessingIndices 映射 */ },
  report:   (data, job) => { /* 只写 #reportLogBox 与 #reportResult */ },
};
```

| 并发任务支持 | 1 个（全局单例） | N 个（Map 注册表） |
| 死代码 | 79 行（4077–4155）+ 1 死变量 | 0 |
| 覆盖式补丁 | 1 处（4888–5120） | 0 |

### 10.1 关键风险提示 ⚠️

**关于第 6 项（参数折叠）的实现约束：**

`collectParams()`（2954–3040）通过 `document.getElementById()` 直接读取控件当前值。**折叠实现必须使用 `display:none` 显隐，绝不能采用「惰性渲染 / 延迟创建 DOM」策略** —— 后者会使折叠状态下的控件从 DOM 中消失，导致 `collectParams()` 读到 `null`，静默丢失参数配置（例如用户展开了 Okaa 设置后又折叠，启动转换时 Okaa 参数全部丢失）。

现有 `toggleCollapse()`（1926）已是正确的显隐实现，**直接复用其模式即可**。

**关于第 7 项（元数据组件化）的约束：**

`p_` / `m_` / `me_` 三套 id 前缀被 `collectParams()`、`applyParams()`、`getDefaultMetaSettings()`、`saveMetaFileSettings()` 等多处硬编码引用。组件化时**必须生成完全相同的 id**，否则会静默失效。建议先写好 id 对照表，改造后逐项核对。

## 十二、更优实现方式建议

以下为可选的更优方案，均**不影响现有功能兼容性**，供决策参考：

| # | 现状 | 更优方案 | 收益 | 前置条件 |
|---|------|---------|------|---------|
| 1 | 170 个函数全部内联在单个 `<script>` | ES Module 拆为 8–10 个文件（`store.js` / `poll.js` / `renderers/` / `meta.js` / `map.js` / `codec.js` / `ui.js`），用 esbuild 打包回单文件 | 可维护性质变；保留单文件交付形态 | 引入轻量构建步骤 |
| 2 | 无类型检查 | JSDoc + `tsc --checkJs`（不产出构建物） | 提前捕获参数对象字段错误 | 无 |
| 3 | 无测试 | Node 内置 `node:test` 覆盖纯函数（`esc` / `formatDuration` / `fmtTime` / `gcj02ToWgs84` / `wgs84ToGcj02` / `splitSphericalMode` / `calcTimeEstimates`） | 零依赖即可建立测试基线 | 无 |
| 4 | 表格 `innerHTML` 全量重建 | 表格行改为 `<template>` 克隆 + 增量更新（沿用现有增量日志的思路） | 数百行任务时消除卡顿，保持滚动位置与焦点 | 无 |
| 5 | 148 处内联事件 | 事件委托：容器上绑一次 `click`，通过 `data-action` 分发 | 可启用 CSP；集中管理交互 | 需与 P2 同步 |
| 6 | 前后端参数无契约校验 | 后端增加参数 schema 校验（白名单 + 类型），前端错误提示更明确 | 防止非法参数导致 ffmpeg 静默失败 | 后端改动（本轮不做） |
| 7 | 元数据工具与报告同属「元数据」命名族 | 强化语义区分：工具标注「写入」、报告标注「只读」，图标与主按钮文案区分 | 降低误操作 | 无 |

> **关于「是否引入框架」的立场**：**不建议**。本项目是桌面单窗口应用、6 个模式、无路由需求、无 SSR 需求，原生 JS 已足够。引入 Vue/React 会带来构建链、依赖维护、包体积的三重成本，而当前真正的痛点是**结构组织**而非**渲染能力**。把原生代码分模块组织好，收益远大于换框架。

| **好在哪** | ① 功能完整度与密度高（6 模式 / 170 函数 / 8 编码器 / Insta360 与 Okaa 专项支持）；② 零依赖风险，Leaflet 本地化到位；③ 增量日志渲染、Tooltip 单例、编码器自检、诊断导出等多处细节体现了成熟的工程直觉；④ 发布链完整（多语言安装包 + 单一版本源） |
