# ADR-004: 元数据队列快照与待转换状态机

## Status

Accepted (2026-03-11, v3.13.13 增量)

## 背景

360video-converter 是 Flask + pywebview 桌面应用，前端纯 JS 多文件模块化。元数据工具（`#metadataMode`）当前有两处能力缺口，且「批量执行列表」的数据模型无法支撑「先排队、后统一执行」的工作流：

1. **入队不快照**：现有 `addToMetaBatchList()`（`static/js/50-meta.js:13`）用 `getDefaultMetaSettings()`（等价 `collectMetaSettings('m')`，`50-meta.js:175`）作为 `settings` 写入队列项 —— 这只是**读了一遍当前全局面板**。用户随后在界面上改参数，已入队项的 `settings` 不会跟着变（这是好的），但用户**无法知道自己入队的那一刻到底冻结了什么**（这是坏的）：入队后立刻改全局输出目录，执行时所有项统一读 `#metaBatchOutDir`（`60-jobs.js:695`、`:710`），于是「入队时的输出目录」与「执行时的输出目录」语义不一致。
2. **执行判定与队列状态脱节**：`startMetadataApply()`（`60-jobs.js:681`）用 `metaBatchItems.filter(f => f.selected)` 判定批量模式，`selected` 是 checkbox 语义；执行开始时把选中项状态无条件重置为 `'pending'`（`60-jobs.js:713`），执行中转 `'processing'`（`60-jobs.js:523`），结束后转 `'done'`/`'error'`（`60-jobs.js:525`、`:528`、`:563`、`:566`）。结果是：已 `done` 的项只要还勾着，下次点击就会被重置成 `pending` 重跑一遍 —— 与「再次点击只跑未完成项」的目标直接冲突。
3. **「浏览」只能选路径不能取日期**：全项目 14 处「输入框 + 浏览按钮」统一走 `data-action="open-path-dialog"` → `openPathDialog(ds)`（`static/js/10-ui.js:485`）→ `openFileBrowser(targetId, isDir, fileFilter)`（`10-ui.js:388`），回填逻辑是 `el.value = data.path` + dispatch change。而三处「手动指定日期」输入框（`#p_manual_date` index.html:587、`#m_manual_date`:878、`#me_manual_date`:1267）需要的是「取所选文件的文件系统创建时间」，与「回填路径」是不同语义，不能塞进现有 `open-path-dialog` 分支。

已确认的四个不可更改决策点（用户侧裁定）：

- D1：「加入批量列队」快照来源 = **仅** `#metaInput` 当前输入框的单个文件；列队中已有文件不动。
- D2：「应用元数据」判定待转换任务 = **执行列队中未完成的项**，执行后标记完成并保留在列队（不移除）；再次点击只跑未完成项。
- D3：「浏览」回填的日期 = **只读文件系统创建时间**（不解析视频 `creation_time` 元数据）。
- D4：每项「输出目录」**随加入快照固定**，不随界面变化。

## 决策

### D-1：`out_dir` 是队列项的一等字段，快照时写入，之后界面不再影响

**决策**：在 `metaBatchItems` 每项上新增 `out_dir: string`，加入快照时从 `#metaBatchOutDir` 读一次并写入该项。执行时输出路径由 `f.out_dir` 决定，`#metaBatchOutDir` 仅作为「兜底默认值」仅在单项 `out_dir` 缺失时使用。

**为什么**：`out_dir` 若继续放在 settings 里，会与 `collectMetaSettings` 的字段契约冲突 —— `collectMetaSettings` 是「元数据标签设置」的统一采集层（D4 决策要快照的正是这一层），输出目录不属于元数据标签，混进去会让 `META_FIELD_IDS` 三前缀映射表（`50-meta.js:51`）多出一组无意义的映射，破坏该表「三个前缀一一对应」的既有不变量。放在顶层则天然是「每项独有」，语义最清晰。

**为什么不用 `#metaBatchOutDir` 全局值**：D4 明确要求逐项固定。全局值是「下一次入队」的默认值，不是「已入队项」的运行时参数。若执行时仍读全局值，则「加入 A（输出目录 X）→ 改全局为 Y → 执行」会写出到 Y，用户配置 X 的意图被静默丢弃 —— 这是典型的沉默逻辑错误（`generated-code-failure-modes.md` §2 最致命一类）。

### D-2：状态机用项目已有的四态，不引入 `running`/`failed`

**决策**：沿用项目**已经在用**的四个状态值 `pending | processing | done | error`，不引入 ADR 任务书里建议的 `running` / `failed`。

**为什么**：brief 中建议的 `pending→running→done/failed` 与代码事实不符。实测 `renderMetaBatchTable()`（`50-meta.js:347-354`）的渲染分支、`renderMetadataJob()`（`60-jobs.js:523-528`）与 `renderJobCompletion()`（`60-jobs.js:563-569`）的状态写入点，使用的已经是 `processing` / `done` / `error`。若改名为 `running`/`failed`，必须同步改 5 个写入点 + 3 个渲染分支 + 回归套件 `_verify_meta_reuse_flows.js` 的断言，属于纯改名风险（破坏性收益为零）。**状态机词汇表必须以代码事实为准，不是以设计稿为准。**

合法迁移：

```
        ┌──────────────────────────── retry (显式「重新排队」) ─────────────────────────┐
        ↓                                                                        │
     pending ──submit──> processing ──ok────> done                                 │
        ↑                    │                                                  │
        │                    ├──failed──> error ──retry-on-next-apply──────────>┘
        │                    │
        └── 用户编辑参数后仍为 pending（编辑不重置执行态）
```

| 起始 | 事件 | 目标 | 合法性 | 写入点 |
|---|---|---|---|---|
| — | 加入列队 | `pending` | 合法 | 新增 `snapshotToMetaBatch()` |
| `pending` | 提交执行 | `processing` | 合法 | `renderMetadataJob` `60-jobs.js:523` |
| `processing` | 成功 | `done` | 合法 | `60-jobs.js:525` / `:563` |
| `processing` | 失败 | `error` | 合法 | `60-jobs.js:528` / `:566` |
| `processing` | 被跳过 | `error` | 合法（`statusMsg='已跳过'`） | `60-jobs.js:569` |
| `done` | 再次点击「应用元数据」 | `done`（不变） | **合法 —— 本次核心修复** | 见 D-4 |
| `error` | 再次点击「应用元数据」 | 重置 `pending` → 重跑 | 合法（失败可重试） | 见 D-4 |
| 任意 | 移除 / 清空 | 项消失 | 合法 | `removeMetaFile` / `clearMetaFiles` |
| `done` | 手动编辑参数 | `done`（不变） | 合法（编辑不隐式重排队） | `saveMetaFileSettings` |

**关键约束**：`done` 项的参数编辑**不**把它打回 `pending`。理由：用户批量微调若干已完成项的参数，期望是「改完再统一重跑」，若编辑即自动重排队，则每改一项就立刻触发一次写文件（10 项 = 10 次 ffmpeg 调用），是资源浪费 + 意外副作用。要重跑有两条显式路径：把 `done` 项勾上并点「应用元数据」（`done` 项被显式重置为 `pending`，见 D-4），或移除后重新加入。

### D-3：「待转换」的定义 = `status !== 'done'`，与 `selected` 正交

**决策**：`selected`（checkbox）**继续参与判定**，规则为：

```
待执行项 = metaBatchItems.filter(f => f.selected && f.status !== 'done')
```

**明确回答 brief 的问题**：「列队里 `selected=false` 但未完成的项要不要跑？」→ **不跑。**

**为什么**（这是本 ADR 最容易被实现错的一处，必须写死）：

1. **产品语义**：`selected` 是用户对「本次要处理哪些」的显式表达。批量执行面板的 checkbox 存在意义就是圈定范围；若 `selected=false` 的项照跑，checkbox 就变成纯装饰，`全选/全不选/移除选中` 三个按钮（`index.html:822-824`）全部失去意义。
2. **数据丢失不可见**：若照跑 `selected=false` 的项，`_metaProcessingIndices`（`50-meta.js:8`）会把这些项的行索引推进映射数组，执行结束后 `renderJobCompletion` 写回状态 —— 用户看到「我没勾的那行也变成完成了」，且没有任何提示。这是沉默逻辑错误，不是 UX 问题。
3. **D2 的落地方式**：D2 说「执行列队中未完成的项」，「未完成」是**在已勾选集合内**的过滤条件（`status !== 'done'`），不是「绕过勾选」。D2 与 `selected` 不冲突，二者是 AND 关系。若 D2 的本意是忽略 `selected`，那 checkbox 就该被删掉，而不是留着假装有用。

**边界情况与规则**：

| 场景 | 行为 | 理由 |
|---|---|---|
| 有 `selected && status!=='done'` 的项 | 走列队批量分支，**忽略界面设置** | 需求 3 明确要求 |
| 列队为空（`length===0`） | 走界面单文件分支 | 无列队可执行，D3 兜底 |
| 列队非空但无任何 `selected && status!=='done'` 的项 | 走界面单文件分支 | 待转换集合为空 = 等价于无可执行项 |
| 列队非空、`selected=true` 的项全部 `done`，但存在 `selected=false` 的 `pending` 项 | 走界面单文件分支 | 用户显式把这些项排除在本次之外；此时若跑列队会违反 `selected`，若提示「无待转换项」又与 `selected=false` 项确实未完成的事实矛盾。**兜底分支优先，且必须在提示文案中说明原因** |
| `#metaInput` 为空且列队无可执行项 | `alert('请选择视频文件，或将文件加入批量列表')` | 沿用 `60-jobs.js:726` 既有文案 |

**「无待转换项」时的用户提示**：走兜底分支前，若 `metaBatchItems.length > 0`，用 `showToast` 明确告知「列队中无待转换项，已按当前界面设置执行」（`info` 级），避免用户以为跑的是列队。这条是需求「界面状态与队列状态实时同步」的一部分 —— 界面必须让用户看见「为什么这次跑的不是列队」。

### D-4：`selected` 语义从「本次要跑」细化为「要跑且未完成」，`done` 项显式重排队

**决策**：`startMetadataApply()` 的批量分支改为：

```js
// 示例，非指定 —— 判定顺序与语义为指定，实现风格随项目现状
const queue = metaBatchItems.filter(f => f.selected);
const runnable = queue.filter(f => f.status !== 'done');

if (runnable.length > 0) {
  // 列队优先：忽略界面设置，按列队顺序（数组下标升序）依次构造 items
  _metaProcessingIndices = [];
  items = [];
  metaBatchItems.forEach((f, i) => {
    if (!f.selected || f.status === 'done') return;
    _metaProcessingIndices.push(i);
    const p = f.settings || globalParams;
    // out_dir 是快照值；空串 = 原地修改（与 #metaBatchOutDir 留空语义一致）
    const out = f.out_dir ? `${f.out_dir}\\${f.name}` : f.path;
    items.push({ input: f.path, output: out, params: p });
    // 仅重置本次真正要跑的项 —— 不再无差别重置全部 selected 项（这是 done 被重跑 的根因）
    f.status = 'pending';
    f.statusMsg = '';
    f.duration = '';
  });
  // 空跑保护：runnable 非空但 items 构造后为空不应发生，此处仅防御
} else {
  // 兜底：界面单文件
  if (metaBatchItems.length > 0) showToast('列队中无待转换项，已按当前界面设置执行', 'info');
  // ...沿用 60-jobs.js:723-733 原逻辑
}
```

**为什么必须用两段过滤（`queue` 再 `runnable`）而不是一次过滤**：`hasAnyFeature` 校验（`60-jobs.js:718`）需要区分「有项但都没开功能」和「无可执行项」两种失败，前者要 `alert` 中止、后者要兜底到界面分支。合成一次过滤会让这两种情况都落进 `runnable.length === 0`，把「中止」误判成「兜底」。

**为什么 `done` 项要能被显式重排队**：`status !== 'done'` 的过滤是「默认不重跑已完成项」，但用户改了 `#metaBatchOutDir` 或改了某项参数后，合理的诉求是「把之前那批再跑一遍到新目录」。过滤条件让 `done` 项永远不进 `items`，这个诉求就无法表达。解法是**显式重排队**：在列队表每行加一个「重新排队」动作（`status: 'done' → 'pending'`），或在编辑弹窗保存时若检测到 `f.out_dir` 变化则提示重排队。**本 ADR 采用前者**（独立动作，语义无歧义，不污染保存流程），登记为 `data-action="reset-meta-item"`，新增 id 登记见「风险与回归点」。

**`items` 构造的三个易错点（逐条钉死）**：

1. **顺序**：按 `metaBatchItems` 下标升序（`forEach` 天然有序）。后端按 `items` 数组顺序串行执行，`_metaProcessingIndices` 是同序映射数组，两者必须同序同长。**不要用 `filter().map()` 两次独立遍历** —— 两次遍历之间若有 DOM 事件插入项，映射会错位。
2. **输出路径分隔符**：`` `${outDir}\\${f.name}` `` 沿用现有反斜杠写法（`60-jobs.js:710` 现状）。本项目是 Windows 桌面应用，ffmpeg 在 Windows 下接受正斜杠，但**混用会产生 `C:\dir/sub.mp4` 这类怪路径**。保持与现状一致，不引入 `os.path.join` 语义。
3. **`output === input` 的原地覆盖场景**：`out_dir` 为空时 `output = f.path`，后端走原地修改路径（`_meta_tool_tests.py` 的 M 系列用例覆盖）。此时 `params` 里 `set_file_created` / `set_file_modified` 会真的改这个文件的 FS 时间 —— 而 D3 的「浏览」读的也是 FS 创建时间。**副作用是链式的**：用户浏览读出日期 A → 写入 → 再浏览读出日期可能不再是 A。这不是 bug（写入确实改了 FS 时间），但必须在验收时知道，别误判为功能不稳定。

### D-5：去重规则 = 路径规范化后比对，已存在项**跳过且不覆盖**

**决策**：加入列队时，用 `normalizePathForCompare()` 归一化后与所有已有项比对；命中则 `showToast('文件已在列表中', 'warning')` 并 return，**既不覆盖已有项的 `settings`，也不新增**。

**为什么「跳过」而不是「覆盖参数」**：覆盖会静默丢弃用户对那一项单独做过的编辑（`editMetaFileSettings` 的存在意义就是逐项独立配置）。用户看到「已在列表中」知道发生了什么；若选择覆盖，界面上没有任何提示说「你之前设的 GPS 被冲掉了」—— 这又是沉默的数据丢失。**去重宁可让用户手动移除后重加，也不替他改配置。**

`normalizePathForCompare()` 规则（Windows 语义）：

```js
// 示例，非指定 —— 归一化维度为「同一文件的几种常见写法」
function normalizePathForCompare(p) {
  if (!p) return '';
  let s = String(p).trim().replace(/^"|"$/g, '');   // 去掉手输时残留的引号
  s = s.replace(/\//g, '\\');                      // 统一分隔符
  s = s.replace(/\\{2,}/g, '\\');                   // 折叠重复分隔符
  s = s.replace(/\\+$/, '');                        // 去尾部分隔符
  return s.toLowerCase();                           // Windows 文件系统大小写不敏感
}
```

**为什么需要这四层归一化**：用户可能从「浏览」按钮拿到 `C:\Users\PC\a.mp4`，也可能手动输入 `c:/users/pc/a.mp4` 或 `C:\Users\PC\.\a.mp4`。现有代码 `metaBatchItems.some(f => f.path === inp)`（`50-meta.js:16`、`:301`、70-report.js:391）是**严格字符串相等**，这类变体会绕过去重产生重复行 → 同一文件被处理两次（第二次读的是第一次的产物，日期/GPS 全部错乱）。**这是本次改动顺带修掉的既有缺陷**，成本 6 行。

**注意**：三处既有去重点（`50-meta.js:16` `addToMetaBatchList` / `50-meta.js:301` `addMetaFileManual` / `70-report.js:391` 报告入队）应**统一改用** `normalizePathForCompare()`。`70-report.js` 的报告入队**不写 `out_dir`**（它没有 `#metaBatchOutDir` 语义）→ 统一写 `out_dir: ''`（原地修改），与 `50-meta.js` 两个入口保持结构一致，否则 `startMetadataApply` 读 `f.out_dir` 时遇到 `undefined` 会走 `f.out_dir ? ... : f.path` 的假值分支，行为恰好正确但依赖了巧合，不可接受。

### D-6：新增后端路由 `GET /api/file_fs_time`，只读文件系统创建时间

**决策**：新增单一新路由，读取**文件系统**创建时间（D3：不解析视频元数据）。

```
GET /api/file_fs_time?path=<绝对路径>

200 {
  "path":     "C:\\Users\\PC\\Videos\\a.mp4",
  "ctime":    "2024-01-15T14:30:00",   // 本地 naive 字符串，直接可填入 manual_date
  "ctime_ts": 1705301400.0,            // Unix 时间戳（调试/二次加工用）
  "mtime":    "2024-01-16T09:00:00",
  "source":   "filesystem"              // 恒为 "filesystem"，预留未来区分来源
}

400 { "error": "缺少 path 参数" }
404 { "error": "文件不存在" }
500 { "error": "读取文件时间失败: <OSError 摘要>" }
```

**入参**：用 GET + query（与既有 `/api/probe-source?path=` `app.py:4990` 一致），不用 POST —— 只读、无副作用、无 body。`file_filter` 由前端传给 `/api/native_dialog`（`'video'`），不传给本路由。

**返回 `ctime` 格式必须是本地 naive 字符串**，与 `manual_date` 输入框的既有格式（`2024-01-15` 或 `2024-01-15T14:30:00`，见 index.html:587 placeholder）以及 `utcToLocalNaive()`（`50-meta.js:183`）的输出格式**完全一致**。为什么：后端 `apply_metadata_one` 对 `manual_date` 走 `datetime.fromisoformat()` 解析后**当作本地时间**写入 tag 与 FS 时间；若返回带 `Z` 或偏移量的字符串，会复现 v3.13.7 修掉的「±8h 偏差」缺陷（`50-meta.js:179-182` 注释即此事的记录）。**直接 `datetime.fromtimestamp(os.stat(p).st_ctime).isoformat(timespec='seconds')` 即可，不要加 `Z`、不要 `.astimezone()`。**

**Windows / 非 Windows 兼容策略 —— 这里必须分清两件事**：

| 平台 | `os.stat().st_ctime` 语义 | 本路由行为 |
|---|---|---|
| Windows | **文件创建时间**（CPython 在 Windows 上把 `st_ctime` 映射到 `CreateFileW` 的 `ftCreationTime`） | 直接用，准确 |
| POSIX/macOS | **inode 变更时间**（ctime ≠ birthtime），**不是创建时间** | 仍返回 `st_ctime`，但响应加 `"is_creation_time": false` |

**明确回答 brief 的问题**：**不复用 `set_file_dates` 的 win32 ctypes 方案。** 理由：
- `set_file_dates`（`app.py:509`）是**写**路径 —— 它用 `CreateFileW` + `SetFileTime` 设置时间。本需求是**读**，`os.stat()` 一个系统调用就够，不需要 ctypes、不需要打开句柄。
- 复用写路径的 ctypes 段会引入 `CreateFileW.restype` / `INVALID_HANDLE_VALUE` 等一整套句柄管理复杂度（`app.py:536-571`），只为了读一个 `os.stat` 已有的字段 —— 这是纯粹的成本增加。
- `app.py:2936` 已有先例：读时间用 `os.stat(temp_out)` 拿 `st_ctime` / `st_mtime`，只在写的时候才走 `set_file_dates`。本路由沿用同一分工。

非 Windows 分支保留而非报错：本项目是 Windows 桌面应用（pywebview + PowerShell 原生对话框 + `set_file_dates` 的 ctypes 段都写死 Windows），但 `os.stat` 在两个平台都能跑通。返回 `is_creation_time: false` 让前端能提示「当前系统返回的是文件变更时间」，比直接抛错更有信息量。**不为 Linux 写死代码，也不在 Linux 上假装它是创建时间。**

**为什么不用 `/api/probe-source` 现成路由**：它返回的 `creation_time` 是 ffprobe 读的视频**元数据标签**（`app.py:4990-5030`），D3 明确排除。且它要起 ffprobe 子进程（timeout 30s）—— 为读一个 FS 时间付出一次进程启动不划算。新路由零子进程、零超时，纯 `os.stat`。

### D-7：前端委托链 —— 新增 `data-action="browse-date"`，不改 `open-path-dialog`

**决策**：在 `DELEGATED_ACTIONS`（`00-core.js:212`）**新增一个独立条目** `'browse-date'`，不复用 `open-path-dialog`，也不给 `openPathDialog` 加参数。

```js
// 00-core.js DELEGATED_ACTIONS 新增（示例，非指定 —— 位置在 open-path-dialog 之后）
'browse-date': el => browseDateFromFile(el.dataset.dateTarget),
```

```html
<!-- 三处，示例，非指定 —— 结构与 #metaBatchOutDir 行的 input-group 完全一致 -->
<div class="input-group">
  <input class="input" id="p_manual_date" type="text" placeholder="格式: 2024-01-15 或 2024-01-15T14:30:00">
  <button class="btn" type="button" data-action="browse-date" data-date-target="p_manual_date">浏览...</button>
</div>
```

**为什么不复用 `open-path-dialog` 加参数**（brief 明确要求给出取舍）：

`openPathDialog` 的语义是「打开对话框 → 把**路径**回填到目标输入框 → dispatch change」。它的实现 `openFileBrowser`（`10-ui.js:388-418`）在回填后还带**副作用分支**：`if (targetId === 'singleInput') { updateSingleDatePreview(); outEl.value = ''; }`（`10-ui.js:414-418`）。「读 FS 时间回填日期」需要的是：打开对话框 → 取路径 → **不填进目标框** → 调另一个后端路由 → 填日期 → 触发**日期区**的联动（清文件名日期勾选、刷新预览）。

若复用 `open-path-dialog` 加 `path-mode="date"`，会产生三个问题：
1. `openPathDialog` 必须长出一个「不回填路径」的分支，其内部 `el.value = data.path`（`10-ui.js:410`）不能执行 → 分支里要复刻 `openFileBrowser` 的一半逻辑（取 initial_dir、fetch native_dialog、判 `data.error`），而不是复用。**名义复用、实质复制**。
2. `data-date-target` 与 `data-path-target` 语义混淆后，14 处既有「输入框 + 浏览按钮」的统一约定（`10-ui.js:473-484` 的大段注释明确定义了这个约定）被破坏，后续维护者无法从 action 名判断行为。
3. 门禁 06（`06-data-action-contract.js`）是**双向**校验：使用但未注册 → `exit 1`；注册但未使用 → 仅打印警告。复用会让 `open-path-dialog` 承载两种行为，违反该门禁设计意图（一个 action 一件事）。

**新增独立 action 是三者中唯一「不改既有行为、不复制逻辑、不违反既有约定」的方案。**

`browseDateFromFile()` 实现要点（放 `50-meta.js`，因为它与 `REUSE_TARGETS`/`META_FIELD_IDS` 同域；**不放 `10-ui.js`**，因为 `10-ui.js` 是路径输入层，日期不属于该层职责）：

```js
// 示例，非指定 —— 流程与顺序为指定，实现细节随项目风格
async function browseDateFromFile(targetId) {
  if (!targetId) return;
  let picked;
  try {
    const r = await fetch('/api/native_dialog', {
      method: 'POST', headers: {'Content-Type': 'application/json'},
      body: JSON.stringify({
        type: 'open_file', title: '选择参考文件（读取其文件系统创建时间）',
        file_filter: 'video', path_type: 'open', initial_dir: ''
      })
    });
    const data = await r.json();
    if (data.error) { alert(data.error); return; }
    picked = data.path;
  } catch (e) {
    alert('打开文件对话框失败: ' + e.message); return;
  }
  if (!picked) return;                       // 用户取消

  try {
    const r = await fetch('/api/file_fs_time?path=' + encodeURIComponent(picked));
    const d = await r.json();
    if (d.error) { alert(d.error); return; }
    const el = document.getElementById(targetId);
    if (!el) return;
    el.value = d.ctime || '';
    if (!d.is_creation_time) {
      showToast('当前系统返回的是文件变更时间，非创建时间', 'warning');
    }
    el.dispatchEvent(new Event('change', { bubbles: true }));
  } catch (e) {
    alert('读取文件时间失败: ' + e.message);
  }
}
```

**三个必须有的联动（漏了会产生沉默错误）**：
1. **置 `manual_date` 后必须清掉「从文件名提取日期」勾选**，否则 `onMetaDateFromNameChange`（`50-meta.js:200-206`）的互斥语义会让人以为文件名日期仍生效。`reuseSourceTime`（`50-meta.js:663-664`）就是这么做的（`fromName.checked = false`）。**`p_` 前缀的坑**：`p_date_from_filename` 同时是总开关和子项（`META_FIELD_IDS.dateMaster.p === dateFromName.p`，`50-meta.js:54-55`；`REUSE_TARGETS.p.masterDate === fromName`，`50-meta.js:577`），清掉它等于**关掉整个日期功能**（`collectMetaSettings('p')` 的 `apply_date` 与 `date_from_filename` 取同一个值，`50-meta.js:100-103`）。

   **但既有实现已 neutralize 这个坑，靠的是语句顺序而非特判**：`reuseSourceTime` 先 `fromName.checked = false`、再 `masterDate.checked = true`（`50-meta.js:663-667`），两行对 `p_` 指向**同一个元素**，净效果是「取消勾选后立即重新勾选」= 保持开启。

   **因此实现约束是：必须复用 `reuseSourceTime` 的这两行原始顺序，不得调整、不得为 `p_` 写特判。** 一旦把「确保总开关打开」提前到「清文件名日期」之前，`p_` 侧会净变为「日期功能被关闭」——用户填了日期却什么都不写，且**界面无任何报错**（`p_date_from_filename` 取消勾选会同时触发 `dateOptions` 折叠，用户看到的是「选项区消失了」，很可能误以为自己操作有误）。这是本 ADR 中最隐蔽的一处顺序依赖。
2. **确保日期总开关打开**：`m_` 侧 `m_apply_date`（`REUSE_TARGETS.m.masterDate`）、`me_` 侧 `me_apply_date`。`reuseSourceTime` 的 `50-meta.js:666-667` 已做同样处理，且**正是靠它与上一条的顺序配合才让 `p_` 侧保持开启** —— 复用该函数体而非重写。
3. **三前缀映射必须复用 `REUSE_TARGETS`（`50-meta.js:574-592`），不要另写一份**。`p_`/`m_`/`me_` 的 `manual` / `fromName` / `masterDate` / `showDateSection` / `afterTime` 五元组各不相同（`p_` 的 `afterTime` 刷 `#datePreviewContainer`、`m_` 刷 `#metaDatePreview`、`me_` 为 `null`），手写三份分支等于把既有映射表重新实现一遍 —— 该表存在的唯一理由就是消除这种重复（`50-meta.js:464-471` 的注释记录了 v3.13.4 场景 1 的同类教训）。
4. **dispatch change**：让日期预览区（`#datePreviewContainer` / `#metaDatePreview` / `#me_date_info`）刷新。`openFileBrowser` 也这么做（`10-ui.js:412`），是本项目既有惯例。

**最省事的正确做法**：把 `browseDateFromFile` 的「写入 + 联动」部分**直接复用 `reuseSourceTime` 的联动序列**。建议实现为：先取到 `ctime`，然后复用 `REUSE_TARGETS[prefix]` + `utcToLocalNaive` 那一段联动（抽成一个 `applyManualDateToTarget(prefix, value, sourceLabel)` 供两处调用）。**不要复制粘贴 6 行** —— 复制后两处漂移是时间问题，`_verify_meta_reuse_flows.js` 的 35 个断言里有 5 个直接断言 `me_manual_date` 的联动结果，漂移会立刻被套件抓到（这是好事，但要靠复用而不是靠套件兜底）。

### D-9：徽标计数与界面实时同步

**决策**：`#metaQueueCount` 文案从 `` `${n} 个文件 (${selectedCount} 选中)` `` 扩展为 `` `${n} 个文件 (${selectedCount} 选中, ${pendingCount} 待转换)` ``，其中 `pendingCount = metaBatchItems.filter(f => f.selected && f.status !== 'done').length`。

**为什么必须区分两个计数**：`selected` 是「圈选范围」，`待转换` 是「本次真会跑的数量」。需求明确要求「界面徽标计数同步」且「保持界面显示与队列实际内容一致」。执行完成后，若徽标还显示「5 选中」而实际只跑了 2 项，用户无法判断是否还要再点一次。**`selectedCount` 与 `pendingCount` 分离，是让界面反映 D-3 判定规则的唯一方式。**

同步点（必须全部调用，否则出现「界面与队列不一致」）：
- `renderMetaBatchTable()`（`50-meta.js:338-339`，统一入口）
- `toggleMetaFileSelection()`（`50-meta.js:407-411`，当前只重算 selected，需补 pending）
- `selectAllMetaFiles()` / `removeSelectedMetaFiles()` / `removeMetaFile()` / `clearMetaFiles()` → 都已调 `renderMetaBatchTable()`，自动覆盖
- **新增**：`renderJobCompletion()` 收尾（`60-jobs.js:573` 已调 `renderMetaBatchTable()`，自动覆盖）
- **新增**：新「重新排队」动作后显式重算

**空态 colspan**：`renderMetaBatchTable` 空态行用 `colspan="7"`（`50-meta.js:335`），表头也是 7 列（`index.html:831-833`）。本 ADR **不加列**（输出目录在「任务内容」徽标区以 `title` 提示呈现，见下），所以 colspan 不变。加列会同时改 `index.html` 表头、`:335` 空态、以及 `:387-398` 行模板三处，且 `colspan` 与实际列数不一致在部分渲染器下不报错但显示错位 —— 不值得。

**输出目录的可视化**：不新增表格列，改为在「任务内容」单元格追加一个 `meta-badge` 徽标，显示输出目录（截断 + `title` 全路径），并入 `50-meta.js:357-385` 的 `taskBadges` 数组。**理由**：与既有「全景元数据 / 写入日期 / GPS」三类徽标风格一致，不改表格结构，改动面最小。徽标内容用 `esc()` 转义（铁律 5）。

### D-10：输出目录编辑能力（需求 2）—— 补齐到与主界面一致

**决策**：在 `#metaEditModal`（列队单行编辑弹窗）内新增「输出目录」字段，与其余可编辑项对齐。

- 新增输入框 `id="me_out_dir"`（`me_` 前缀，与弹窗内其余字段一致）
- 新增「浏览」按钮 `data-action="open-path-dialog"` + `data-path-target="me_out_dir"` + `data-path-dir="true"` —— **这里是复用 `open-path-dialog` 的正确场景**（选目录 → 回填路径），与 D-7 的「读时间」场景性质不同，故不冲突
- `editMetaFileSettings()` 回填 `me_out_dir` = `f.out_dir || ''`
- `saveMetaFileSettings()` 保存 `f.out_dir = me_out_dir.value.trim()`
- **必须同时做**：`META_FIELD_IDS` **不新增** `outDir` 条目。输出目录不是元数据标签设置（见 D-1），`me_out_dir` 由 `edit/saveMetaFileSettings` 单独读写，不进 `collectMetaSettings`/`applyMetaSettings`。理由：这两函数是「三前缀一一对应」的元数据标签采集层，把 `out_dir` 塞进去会让 `p_`/`m_` 前缀出现无意义映射（主界面没有 per-item 输出目录概念）。

**放置位置**：日期区块之后、GPS 区块之前。理由：输出目录是「产物去哪」而非「标签写什么」，视觉上应与「写入文件的元数据内容」分隔；紧邻日期区块也符合「日期与文件属性」的用户心智连续性。

**弹窗内日期浏览按钮的联动**：`me_` 前缀走 `REUSE_TARGETS.me`（`50-meta.js:586-591`），`fromName` = `me_date_from_filename`、`masterDate` = `me_apply_date`、`showDateSection` = `setMetaSectionVisible('me','date',...)`、`afterTime` = `null`（弹窗不刷新预览）。复用即自动正确。

## 明确不做（out-of-scope）

- **不引入数据库持久化队列**。`metaBatchItems` 是纯内存 `let`（`50-meta.js:6`），刷新即丢。本次需求无「跨会话队列」诉求，加持久化会牵出 schema、迁移、多用户并发，是纯粹的范围蔓延。
- **不改后端 `apply_metadata` 的 `params`/`items` 契约**。`/api/apply_metadata`（`60-jobs.js:735`）的请求体形状不变；`out_dir` 在前端就被翻译成绝对 `output`，后端不需要知道「输出目录」这个概念。
- **不做队列项的拖拽排序**。列队顺序 = 入队顺序 = 数组下标顺序（`_metaProcessingIndices` 依赖同序映射），插队排序会破坏该映射的设计前提。
- **不做测试模式（`test_duration`）的入队快照**。`p_test_encode` / `#testDuration` 属转换族，不在元数据工具路径上。
- **不为 `is_creation_time: false`（非 Windows）做 GUI 降级**。项目是 Windows 桌面应用，该分支只做「如实告知」，不做「换用别的日期来源」。
- **不改 `10-ui.js` 的 `openPathDialog` / `openFileBrowser` / `renderPathField` 任何一行**。新能力走新增路径，避免触碰 14 处既有路径输入框。
- **不给 `me_out_dir` 加「留空 = 用全局输出目录」的混合语义**。D4 要求快照固定；若留空能回退到全局值，就破坏了「固定」且产生隐式依赖。留空 = 原地修改（与 `#metaBatchOutDir` 留空语义一致）。

**注意**：三个「浏览」按钮**刻意不给 id**。理由：它们的唯一身份由 `data-date-target` 表达（指向被填的输入框），给 id 只会多一处必须同步维护的契约。若后续人工验收需要选择器，用 `[data-action="browse-date"][data-date-target="p_manual_date"]` 定位即可。这也让 `EXPECTED_ADDED` 只增 2 项而非 5 项，门禁 05 的登记面最小。

`_verify_meta_reuse_flows.js` 里有 5 处直接断言 `me_manual_date` 及其联动（`:151`、`:154`、`:167-169`、`:171-172`），是 D-7 联动的第一道防线。

**第三步：端到端手测（覆盖核心成功流 + 关键错误流）**

核心成功流：
1. 启动 exe → 切到元数据工具模式 → 确认动作栏只出现「应用元数据」+「加入批量列队」，**不出现**「加入批量队列」（转换族的）。
2. 选一个视频 → 设日期/位置/球面 → 设输出目录 `D:\out1` → 点「加入批量列队」→ 队列出现 1 项，徽标显示 `1 个文件 (1 选中, 1 待转换)`。
3. **改全局输出目录为 `D:\out2`，改日期参数** → 再点「加入批量列队」加入第 2 个文件 → 徽标 `2 个文件 (2 选中, 2 待转换)`。
4. 点「应用元数据」→ **两个文件都应输出到 `D:\out1`**（第 2 项的快照是在改成 out2 之前？不 —— 第 2 项是改全局后加入的，快照应为 `D:\out2`）。**修正验证：第 1 项 → `D:\out1`，第 2 项 → `D:\out2`**。这是 D4 的核心断言。
5. 执行完 → 徽标变 `2 个文件 (2 选中, 0 待转换)`，两行状态「完成」。
6. **再次点「应用元数据」** → 应弹 toast「列队中无待转换项，已按当前界面设置执行」，且**不重复处理前两个文件**。这是 D-4 修复的核心断言（原代码会重跑）。

关键错误流：
7. 同一文件点两次「加入批量列队」→ toast「文件已在列表中」，队列仍 1 项。
8. 用 `c:/users/pc/...` 小写斜杠形式对同一文件入队 → 应被归一化拦下（D-5）。
9. 在编辑弹窗里改某项输出目录并保存 → 徽标区该行出现输出目录徽标 → 点「应用元数据」该项输出到新目录。
10. 点「浏览」选一个文件 → 日期框填入 `YYYY-MM-DDTHH:MM:SS` → 确认「从文件名提取日期」被清勾选、日期总开关被打开、预览区刷新。
11. 取消勾选某 `pending` 项 → 点「应用元数据」→ **该项不应被处理**（D-3）。
12. 已 `done` 的项点「重新排队」→ 徽标 `待转换` 从 0 变 1 → 点「应用元数据」该项被重跑（D-4）。

## 后果

正面：
- 「加入批量列队」成为配置冻结动作，用户对「这批文件用什么参数、输出到哪」有确定性预期（D4 落地）。
- 「应用元数据」从「checkbox 驱动」变为「队列状态驱动」，可重复点击、可增量执行（D2 落地），修掉 `done` 项被无差别重置重跑的既有缺陷。
- 「浏览」按钮让手动日期可从参考文件一键取值，且不与 14 处路径浏览的既有约定冲突（D-7 三方案中最干净的一个）。
- 顺带修掉严格字符串相等去重导致的重复行缺陷（D-5）。

负面 / 待承担的成本：
- 队列项多 2 个字段（`out_dir` + `selected` 语义细化），三处入队入口必须统一改调 `snapshotToMetaBatch`，漏一处则该入口产出结构不一致的项（`out_dir` 为 `undefined`）。这是本改动最主要的扩散风险，用「三处必须同时改」的单文件收敛来控制。
- `selected` 语义从「本次要跑」变为「圈选 + 未完成」，用户需理解两个计数的区别。靠徽标双计数（D-9）表达；文案「待转换」是新增词汇，需在按钮 tooltip 或首次提示中说明 —— **本次实现仅加 `title` 提示，不做引导弹窗**（避免超出需求范围）。
- 后端新增一个只读路由，前端多一次 fetch（`/api/file_fs_time`，无子进程，实测开销为一次 `os.stat` + 一次 HTTP 往返，可忽略）。
- 「重新排队」是 D-4 为「`done` 项无法重跑」开的显式出口，属额外 UI 面。若实现时发现产品更希望「编辑已选项即重排队」，需改 D-2 的关键约束并同步调整 `saveMetaFileSettings` —— **改动前先回写本 ADR**（活规格纪律）。
